# Engine v0.42 — LightComponent (scene-driven lighting)

## Problem

After v0.41, geometry is fully scene-driven — `MeshComponent`/`ModelComponent`
entities are collected and submitted by `Scene::render`. Lighting is not.
Every game still hand-sets its lights each frame in `onRender`:

- `scene_demo`, `csm_demo`, `controller_demo` call
  `renderer.setLightDirection(...)` + `renderer.setPointLights({})`.
- `arena`, `shooter`, `models`, `particles`, `camera_demo`, `billboard_demo`,
  `normalmap_demo`, `parallax_light_demo` build a local
  `std::vector<engine::PointLight>` and call `renderer.setPointLights(...)`.

This is exactly the per-game boilerplate that `MeshComponent`/`ModelComponent`
removed for geometry, and it has been reserved across the last several slices.
v0.42 closes it: a data-only `LightComponent`, a pure GL-free collection pass,
`Scene::render` wiring, and two game migrations that prove both light paths.

## Today's lighting API (unchanged by this slice)

- `Renderer::setLightDirection(const glm::vec3& dir)` — a **single** directional
  light. Its vector drives CSM shadows and the IBL environment
  (`Renderer.cpp:51,264`). Only one directional light is honored. Games pass a
  "toward-light" vector (e.g. `normalize({0.5, 0.7, 0.35})`).
- `Renderer::setPointLights(const std::vector<PointLight>&)` — where
  `PointLight { glm::vec4 positionRadius; glm::vec4 color; }` packs xyz+radius
  and rgb+intensity (std140). The renderer already sorts point lights nearest-N
  by camera distance (`Renderer.cpp:227-239`), so the collection pass does not
  sort or cap.

## Design

### `LightComponent` (data-only, own header)

`engine/scene/LightComponent.hpp`, kept in its own header like `MeshComponent`
and `ModelComponent` so `Components.hpp` stays free of renderer/asset deps:

```cpp
#include <glm/glm.hpp>

namespace engine {

enum class LightType { Directional, Point };

struct LightComponent {
  LightType type      = LightType::Point;
  glm::vec3 color     = glm::vec3(1.0f);
  float     intensity = 1.0f;
  float     radius    = 10.0f;  // point lights only; ignored for directional
};

}  // namespace engine
```

Decision: **one tagged struct**, not two separate components. A game thinks in
terms of "a light," it mirrors the single-struct shape of
`MeshComponent`/`ModelComponent`, and the collection pass walks one view. A
directional light ignores `radius` (documented); its position field is unused
as a position — see below.

### `collectLights` (pure, GL-free, header-only)

`engine/scene/LightCollection.hpp`, an inline free function like
`modelRenderTransform` in `ModelTransform.hpp` — header-only so it needs no new
`.cpp` in the GL-free `bot_arena_tests` source list:

```cpp
#include <vector>
#include <entt/entt.hpp>
#include <glm/glm.hpp>
#include "engine/renderer/PointLight.hpp"
#include "engine/scene/Components.hpp"       // TransformComponent
#include "engine/scene/LightComponent.hpp"

namespace engine {

struct CollectedLights {
  std::vector<PointLight> points;
  bool      hasDirectional = false;
  glm::vec3 directionalDir  = glm::vec3(0.0f, 1.0f, 0.0f);
};

inline CollectedLights collectLights(const entt::registry& reg) {
  CollectedLights out;
  auto view = reg.view<const TransformComponent, const LightComponent>();
  for (const entt::entity e : view) {
    const TransformComponent& t = view.get<const TransformComponent>(e);
    const LightComponent& lc = view.get<const LightComponent>(e);
    if (lc.type == LightType::Point) {
      PointLight pl;
      pl.positionRadius = glm::vec4(t.translation, lc.radius);
      pl.color = glm::vec4(lc.color, lc.intensity);
      out.points.push_back(pl);
    } else if (!out.hasDirectional) {  // first directional wins
      out.hasDirectional = true;
      out.directionalDir = glm::normalize(t.translation);
    }
  }
  return out;
}

}  // namespace engine
```

Semantics:

- **Point light** — position is `TransformComponent.translation`; radius from
  `LightComponent.radius`; color/intensity from the component. No cap or sort
  here (the renderer does nearest-N).
- **Directional light** — direction is `normalize(TransformComponent.translation)`,
  i.e. the same "toward-light" vector games pass today, expressed as the light
  entity's translation. **First directional in view order wins**; later
  directional entities are ignored (the renderer honors only one). Documented
  and unit-tested.
- Directional `radius` is unused; a directional entity is never emitted as a
  point light (the `type` gate ensures it).

### `Scene::render` wiring (engine-lib-only)

`SceneRender.cpp` (the engine-lib-only translation unit that keeps
`bot_arena_tests` GL-free) gains, right after `renderer.setCamera(cu)`:

```cpp
const CollectedLights cl = collectLights(m_registry);
if (!cl.points.empty()) renderer.setPointLights(cl.points);
if (cl.hasDirectional)  renderer.setLightDirection(cl.directionalDir);
```

**The rule is additive: `Scene::render` sets only what the scene declares, and
never clears.** This is load-bearing. During this slice only scene_demo and
arena carry light entities; the other ~8 light-setting games still call
`renderer.setPointLights(...)` / `setLightDirection(...)` in their own
`onRender` *before* `m_scene.render(...)`. If `Scene::render` called
`setPointLights(cl.points)` unconditionally, those games — whose `cl.points` is
empty because they have no `LightComponent` entities — would have their
manually-set point lights wiped every frame. Guarding on `!cl.points.empty()`
(and `hasDirectional`) makes `Scene::render` a no-op for lighting on any scene
without light entities, so non-migrated games are completely unaffected.

Consequences for the two migrated games: arena declares 4 point entities and no
directional, so `Scene::render` sets its point lights and leaves the directional
at the renderer default — exactly arena's current behavior. scene_demo declares
1 directional and no point entities, so `Scene::render` sets its directional and
does not touch point lights (which were already empty). A later slice that
migrates *every* light-setting game could switch to an authoritative rule
(always set, clearing what the scene omits); until then, additive is required
to avoid regressing the un-migrated games.

### Migrations (proofs)

**scene_demo** (directional path). Replace:

```cpp
renderer.setLightDirection(glm::normalize(glm::vec3(0.5f, 0.7f, 0.35f)));
renderer.setPointLights({});
```

with a single directional light `SceneObject` created in `onAttach`: a light
entity whose `TransformComponent.translation = {0.5f, 0.7f, 0.35f}` and
`LightComponent{ LightType::Directional, ... }`. `onRender` drops both manual
calls; `Scene::render` now sets the light. `collectLights` normalizes the
translation to the identical directional vector, so the frame is unchanged.

**arena** (point path). Replace the per-frame 4-light vector build:

```cpp
std::vector<engine::PointLight> lights;
const glm::vec3 palette[4] = {...};
for (int i = 0; i < 4; ++i) { ... lights.push_back(pl); }
renderer.setPointLights(lights);
```

with four point-light `SceneObject`s created once in `onAttach`, each carrying
`TransformComponent.translation = {sx, 2.0f, sz}` and
`LightComponent{ LightType::Point, palette[i], 3.0f, 8.0f }`. `onRender` drops
the vector build and the `setPointLights` call. The four `PointLight` values
produced by `collectLights` are identical to the hand-built ones; the renderer
sums point-light contributions (order-independent for a fixed set), so the
lit frame is unchanged.

## Testing

- **`tests/test_light_collection.cpp`** (GL-free, added to `bot_arena_tests`):
  - point conversion — `translation`/`radius`/`color`/`intensity` land in the
    right `PointLight` lanes;
  - directional — `directionalDir == normalize(translation)`, `hasDirectional`
    true;
  - **first-directional-wins** — two directional entities, only the first's
    direction is used, `points` empty;
  - empty registry — no points, no directional;
  - mixed — N point + 1 directional produces N points and the directional.
- `LightCollection.hpp` is header-only inline, so no change to the GL-free
  source list is needed beyond the new test file.
- **Screenshot gates** — `scene_demo` and `arena` each verified with
  `BOTARENA_SCREENSHOT=<path> ./build/<game>` against a pre-migration baseline;
  target AE ≈ 0 (AA/rounding noise only).

## Non-goals / reserved for later slices

- **Migrating the remaining light-setting games** — shooter, models, particles,
  camera_demo, billboard_demo, normalmap_demo, parallax_light_demo,
  csm_demo, controller_demo. Only scene_demo + arena migrate here (one proof
  per light path); the rest sweep in a follow-up.
- **Multiple directional lights** — the renderer honors one; `collectLights`
  keeps the first and ignores the rest. No aggregation/priority beyond
  view order.
- **Light animation/movement components** — lights are static entities here;
  a game that wants to move a light mutates its `TransformComponent` (no new
  per-frame sync path is introduced).
- **Sort/cull/instancing** and the **`addComponent<T>` empty-tag fix** remain
  reserved from prior slices.

## Decisions table

| Decision | Choice | Why |
|---|---|---|
| Component shape | one tagged `LightComponent{type,color,intensity,radius}` | mirrors Mesh/Model single-struct; one collection view; a game thinks "a light" |
| Directional direction source | `normalize(TransformComponent.translation)` | identical to the vector games pass today; no forward-vector convention; mechanical migration |
| Multiple directionals | first in view order wins | renderer honors exactly one directional |
| Wiring is additive | guard both setters (`!points.empty()`, `hasDirectional`) | `Scene::render` sets only what the scene declares; never wipes the manual lights of the ~8 un-migrated games |
| No-directional scene | `setLightDirection` not called | preserves arena's current renderer default (arena never sets it) |
| Point cap / sort | left to the renderer (nearest-N) | already implemented in `Renderer.cpp` |
| Collection location | header-only inline `collectLights` | GL-free + no new `.cpp` in the tests source list (like `ModelTransform.hpp`) |
| Wiring location | `SceneRender.cpp` (engine-lib-only) | keeps `bot_arena_tests` GL-free |
| Migration scope | scene_demo (directional) + arena (point) | one screenshot-gated proof per light path; low-risk, already on Scene |
