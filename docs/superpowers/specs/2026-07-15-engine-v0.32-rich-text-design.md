# Engine v0.32 — Rich Text (Span List) — Design Spec

**Date:** 2026-07-15
**Status:** Approved for planning
**Scope:** Draw a run of text as an ordered list of styled spans in a single call, so different characters/segments carry different styles (color, outline, glow, shadow — anything in `TextStyle`) within one batch. Reuses the v0.30 style-table seam; no shader/UBO/GPU changes. Styling boundaries change style only — never text geometry.
**Builds on:** v0.28–v0.30 text system (now on `main`). Branches from `main`; rebase after PR #33 (unrelated orbit fix) lands to validate against the corrected head.

## 1. Goal & Motivation

Text today is drawn with one `TextStyle` for the whole string. The Slice-3 style table already
carries many styles per batch (per-glyph `styleIndex` into a per-batch UBO), so rich text is a
**layout + submission** change, not a GPU change: assign each glyph the `styleIndex` of the span
it belongs to.

The critical correctness requirement: **a style boundary must not alter shaping.** Rendering
`"AV"` as one span and as `{"A", s1}, {"V", s2}` must produce identical glyph positions. This
rules out a "lay out each span independently, then offset" approach — that lays out twice and
would drop kerning / pen state across the boundary. Instead, layout runs **continuously** across
spans through a stateful seam; only the style attached to the emitted glyphs changes at a
boundary.

## 2. Decisions (locked)

| Decision | Choice |
| --- | --- |
| Representation | Ordered `TextSpan { std::string_view text; TextStyle style; }` list |
| Renderer boundary type | `std::span<const TextSpan>` (accepts vector/array/any contiguous range; C++20 is enabled) |
| Layout | A **stateful append seam** that carries pen (and a reserved kerning hook) continuously across spans; `layoutText` is refactored onto it so there is one layout core |
| Geometry invariant | Span boundaries change style only — never pen position, shaping, kerning, or missing-glyph behavior. `"AV"` split == `"AV"` whole |
| Double layout | Eliminated — each span is laid out exactly once, appended to the shared quad buffer |
| `TextSpan::text` lifetime | `std::string_view`; submission is synchronous — the renderer does **not** retain it (documented) |
| Empty spans | Ignored: do not move the pen and do not allocate a style-table entry |
| Invisible spans (all spaces/missing) | Advance the pen (as layout dictates) but allocate **no** style entry (no visible glyph uses it) |
| >64 styles in one rich run | Flow into additional batches via `acquire`'s existing cap-split (deterministic); glyph positions stay continuous (layout state is independent of batching). No silent clamp / wrong-style reuse |
| Spaces/tabs/newlines/fallback/UTF-8 | Preserved exactly as the existing layout path (byte-as-codepoint today; real UTF-8/newlines remain as they are — reserved) |
| Single-style `drawText` | Delegates internally to the span path with one span, so the two paths cannot drift |
| Span coalescing | Not needed for v0.32 — equal consecutive styles dedup naturally via `acquire` |
| Deferred | Markup parser (`[c=red]…[/c]`), gradient-across-a-run, mixed fonts/sizes per span |

## 3. Components & changes

### 3.1 `TextSpan` (new header `engine/renderer/text/TextSpan.hpp`)
```cpp
struct TextSpan {
  std::string_view text;
  TextStyle style;
};
```

### 3.2 Stateful layout seam (`TextLayout.hpp`)
```cpp
struct TextLayoutState {
  float penX = 0.0f;
  float penY = 0.0f;                    // reserved: multiline not yet supported
  std::optional<char32_t> previousGlyph;  // reserved: kerning seam (no kerning today)
};

// Append `text`'s quads to `out`, continuing from `state` and advancing it. Local
// pixel coords, y-down, baseline at penY. Missing/zero-size glyphs advance without
// a quad (identical to the current layout). Span boundaries are just consecutive
// appendTextLayout calls sharing one state — geometry is unaffected by them.
void appendTextLayout(const GlyphStore& glyphs, std::string_view text,
                      TextLayoutState& state, std::vector<TextQuad>& out,
                      const MissingGlyphFn& onMissing = {});
```
`appendTextLayout` is the existing `layoutText` body, generalized to (a) start at `state.penX`
instead of `0`, (b) append to `out` instead of returning, (c) update `state.penX` and
`state.previousGlyph`. Behavior for spaces/missing/zero-size glyphs, and the byte→codepoint
handling, are **unchanged**.

`layoutText` is reimplemented on top so there is a single layout core (no drift):
```cpp
inline std::vector<TextQuad> layoutText(const GlyphStore& glyphs,
                                        std::string_view text,
                                        const MissingGlyphFn& onMissing = {}) {
  TextLayoutState s;
  std::vector<TextQuad> out;
  appendTextLayout(glyphs, text, s, out, onMissing);
  return out;
}
```
(Today there is no kerning — `Glyph` carries only `advance` — so `previousGlyph` is written but
not yet consumed; it exists so that when kerning lands, cross-span shaping is already correct.)

### 3.3 `TextRenderer` — span submit is the core
```cpp
void submit(const FontAsset& font, std::span<const TextSpan> spans,
            const TextPlacement& placement, int screenW, int screenH);
```
Logic:
```
if placement.mode != ScreenSpace or screenW<=0 or screenH<=0: return
TextLayoutState state;
std::vector<TextQuad> quads;             // reused across spans; carries continuous pen via state
for (span : spans):
  if span.text.empty(): continue         // empty span: no pen move, no style entry
  const size_t first = quads.size();
  appendTextLayout(font.glyphs, span.text, state, quads);   // continues pen/shaping
  if quads.size() == first: continue     // produced no visible glyph -> no style entry
  auto [batchIdx, styleIdx] = acquire(font.backend, font.atlasRendererID(),
                                      font.pxRange, toGpuStyle(span.style));
  const uint32_t fill = packColor(span.style.fillColor);
  const uint32_t outline = packColor(span.style.outlineColor);
  Batch& batch = m_batches[batchIdx];    // fetch AFTER acquire (may have reallocated)
  for (q : quads[first .. end]):         // apply placement -> NDC, emit 6 verts with fill/outline/styleIdx
      ... (identical to today's per-quad emission)
```
The single-style `submit` becomes a one-span wrapper:
```cpp
void submit(font, text, placement, style, w, h) {
  const TextSpan one{text, style};
  submit(font, std::span<const TextSpan>{&one, 1}, placement, w, h);
}
```
Notes:
- Per-quad → NDC emission is factored into a small helper reused by the loop (no duplication).
- Because layout state is separate from batching, a span whose style triggers `acquire`'s
  cap-split simply emits its (continuously positioned) quads into the new batch. No clamp.
- `quads` is a local buffer; `acquire`/`m_batches` growth never invalidates it.

### 3.4 `Renderer` — span overload
```cpp
void drawText(const FontHandle& font, std::span<const TextSpan> spans,
              const TextPlacement& placement);   // null-font guard; forwards to TextRenderer
```
The existing single-style `drawText(font, text, placement, style)` stays (callers unchanged); it
already routes to the single-style `submit`, which now delegates to the span core.

## 4. Data flow

```
caller: drawText(font, spans{ {"Score: ", white}, {"100", redGlow} }, placement)
  -> TextRenderer.submit(font, spans, placement, w, h):
       state{}
       for each non-empty span:
         appendTextLayout(glyphs, span.text, state, quads)   // pen continuous across spans
         styleIdx = acquire(..., span.style)                 // dedup into batch style table
         emit new quads with styleIdx + packed colors
  -> endFrame: drawTextBatch(..., styles)  (unchanged)  -> single-pass SDF shader (unchanged)
```

## 5. Testing (CPU, no GL — via a stub FontAsset in `tests/test_text_batch.cpp`)

1. **Distinct styles → index boundary:** `{"A",s1},{"B",s2}` ⇒ batch has 2 styles; A's glyph
   `styleIndex==0`, B's `==1`.
2. **Equal styles dedup:** `{"A",s},{"B",s}` ⇒ 1 style entry; both glyphs `styleIndex==0`.
3. **Trailing space advances next span:** `{"A ",s1},{"B",s2}` ⇒ B's `x0 == advance("A")+advance(" ")`.
4. **Split == whole:** `{"AV",s}` vs `{"A",s},{"V",s}` ⇒ identical glyph vertex positions.
5. **Empty spans:** `{"",s},{"A",s}` ⇒ 1 style entry, A at pen 0 (empty span moved nothing);
   `{"",s}` alone ⇒ no batches.
6. **Missing glyphs across spans == single string:** spans containing absent codepoints produce
   the same quads/positions as the concatenated single string.
7. **Single vs one-span equivalence:** single-style `submit` and a one-span rich `submit`
   produce identical geometry and style-table data.
8. **Cap crossing:** a rich run with >64 distinct styles flushes into additional batches (batch
   count > 1) with correct per-glyph indices — the documented behavior, no clamp/wrong reuse.
9. **Layout-state continuity across a span boundary:** a control char (e.g. `'\n'`, currently a
   missing glyph) and pen state carry across the boundary identically to the single-string
   equivalent (multiline is not yet supported, so no vertical break is asserted — this locks the
   state-continuity invariant for when it is).

Existing `[textbatch]`/`[text]` tests stay green (they exercise the refactored `layoutText`).

## 6. Risks & mitigations

- **Geometry drift at span boundaries.** The whole point of the stateful seam. Mitigation: test
  4 (`"AV"` split==whole) and test 7 (single==one-span) lock it; layout runs once, continuously.
- **Dangling `string_view`.** `TextSpan::text` must outlive the synchronous `submit`. Mitigation:
  documented non-retention; submission consumes spans within the call.
- **Reallocation across `acquire`.** `quads` is a separate local buffer; the `Batch&` is fetched
  after `acquire` each span — same discipline as the existing single-style submit.
- **>64 styles.** Deterministic cap-split into additional batches; test 8 covers it.
- **Refactor regressions in `layoutText`.** Mitigation: `layoutText` is a thin wrapper over
  `appendTextLayout`; the existing layout tests re-validate it unchanged.

## 7. Open items (deferred, not blocking)

- Markup parser front-end emitting spans (`[c=red]…[/c]`).
- Gradient interpolation across a run (smooth per-glyph color).
- Mixed fonts/sizes per span (font-families; still reserved).
- Real UTF-8 decoding, kerning (consume `previousGlyph`), and multiline (`penY`) — the seams
  exist; the behavior is unchanged this slice.
