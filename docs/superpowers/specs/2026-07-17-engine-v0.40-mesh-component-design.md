# Engine v0.40 — MeshComponent + Scene::render + arena/shooter Migration — Design Spec

**Date:** 2026-07-17
**Status:** Approved for planning
**Scope:** Add a `MeshComponent` and `Scene::render(Renderer&, aspect)` so the scene draws its own `<Transform, Mesh>` entities through the primary camera; migrate the two scene demos to it as a low-risk proof; and migrate `arena` and `shooter` off their ad-hoc `entt::registry` + manual `MeshRenderer` submission onto `Scene` (single `TransformComponent` source of truth, `MeshComponent`, `Scene::render`, and a scene camera controller).
**Builds on:** the scene model on `main` (v0.38 Scene/SceneObject/TransformComponent/CameraComponent/cameraUniforms/MatrixCamera; v0.39 controller components/systems + quaternion `TransformComponent`).

## 1. Goal & Motivation

v0.38–v0.39 gave the engine a scene graph (entities, transforms, a primary camera, controllers) but the renderer still has to be fed meshes by hand in each game's `onRender`. `MeshComponent` + `Scene::render` close that loop: an entity with a transform and a mesh is drawn automatically. Migrating `arena` and `shooter` — the two gameplay-heavy games that already use a bare `entt::registry` — proves the scene model on real games and removes their duplicated camera/registry/submission boilerplate, giving the engine one coherent entity+render path.

## 2. Decisions (locked)

| Decision | Choice |
| --- | --- |
| `MeshComponent` | Data-only `{ MeshHandle mesh; MaterialHandle material; }` in its own header (`MeshHandle`/`MaterialHandle` are `uint16_t` from `RenderCommand.hpp`) |
| `Scene::render` | `void render(Renderer&, float aspect)` — sets the renderer camera from `cameraUniforms(aspect)`, then submits every `<TransformComponent, MeshComponent>` via an internal `MeshRenderer` (+`MatrixCamera`) using `localTransform()` |
| Lighting | Stays game-set (`setLightDirection`/`setPointLights` before `scene.render`); a `LightComponent` is reserved |
| Migration principle | ONE transform per entity: replace each game's `Transform` with the engine `TransformComponent` (no two-transform sync). Game-specific components (Velocity/Health/Player/Bot/Enemy/Bullet) stay in the scene registry |
| Static geometry | Arena walls + ground (and shooter equivalents) become `SceneObject`s with `TransformComponent` + `MeshComponent`, created once |
| Camera | Games drop the standalone `OrbitCameraController` for a scene camera entity with `OrbitControllerComponent`, mapped from their current orbit params |
| Testing | `MeshComponent` is trivial data; `Scene::render` needs a live GL `Renderer`, so it is screenshot-verified. Migrations preserve behavior — the existing gameplay unit tests (`test_steering`/`test_wall_bounce`/`test_agent_collision`/shooter's) stay green |
| Untouched | The standalone camera classes stay (other games still use them); retiring them is a later slice |
| Reserved | `LightComponent`; sort/cull in `Scene::render`; instanced submission; retiring standalone controllers |

## 3. Components & changes

### 3.1 `MeshComponent` (`engine/scene/MeshComponent.hpp`)
```cpp
#include "engine/renderer/RenderCommand.hpp"  // MeshHandle, MaterialHandle (uint16_t)
namespace engine {
struct MeshComponent {
  MeshHandle mesh = 0;
  MaterialHandle material = 0;
};
}
```
Its own header so `Components.hpp` stays free of renderer dependencies.

### 3.2 `Scene::render` (`Scene.hpp` + `Scene.cpp`)
`Scene.hpp` forward-declares `class Renderer;` and adds:
```cpp
void render(Renderer& renderer, float aspect);
```
`Scene.cpp` (includes `Renderer.hpp`, `MeshRenderer.hpp`, `MatrixCamera.hpp`, `MeshComponent.hpp`):
```cpp
void Scene::render(Renderer& renderer, float aspect) {
  const CameraUniforms cu = cameraUniforms(aspect);
  renderer.setCamera(cu);
  MatrixCamera cam(cu.view, cu.projection);
  MeshRenderer meshes(renderer.queue(), renderer.registry(), cam);
  auto view = m_registry.view<TransformComponent, MeshComponent>();
  for (const entt::entity e : view) {
    meshes.submit(view.get<MeshComponent>(e).mesh,
                  view.get<MeshComponent>(e).material,
                  view.get<TransformComponent>(e).localTransform());
  }
}
```
Note `renderer.registry()` is the **ResourceRegistry** (mesh/material lookup), distinct from the scene's `entt::registry`. Lighting and HUD text remain the game's responsibility.

### 3.3 Scene-demo migration (`scene_demo`, `controller_demo`)
Each visual `SceneObject` gains a `MeshComponent{cube, material}` at creation; `onRender` drops the manual `m_visuals` loop + `MeshRenderer`/`MatrixCamera` and calls `scene.render(renderer, aspect)` after setting lights. Screenshots must be byte-comparable to the pre-migration output (same camera, same transforms).

### 3.4 Arena migration (`games/arena/`)
- `entt::registry m_registry` → `engine::Scene m_scene`; all `m_registry.*` become `m_scene.registry().*` (or via `SceneObject`).
- Delete arena's `Transform`; use `engine::TransformComponent`. Rewrite gameplay accesses: `.position` → `.translation`; the uniform `float scale` → `.scale` (`glm::vec3`), passing `.scale.x` where the steering/collision/wall-bounce helpers want a scalar. `Velocity`/`Health`/`Player`/`Bot` unchanged, stored in the scene registry.
- Player + bots created as `SceneObject`s (`createObject` → set `TransformComponent`, add `Velocity`/`Health`/tag + `MeshComponent{cube, playerMat|botMats[i%4]}`). Walls (4) + ground created once as static `SceneObject`s with `TransformComponent`(translation+scale) + `MeshComponent`.
- `onRender`: set lights, then `scene.render(renderer, aspect)`; keep the HUD/damage text. Bot color is fixed per-bot at creation (`m_botMats[i%4]`) — visually equivalent to today's per-frame index coloring.
- Camera: `OrbitCameraController` → a camera `SceneObject` with `CameraComponent` + `OrbitControllerComponent` mapped from arena's current `setTarget`/`setOrbit` values; `scene.update(dt)` drives it (existing `BOTARENA_ORBIT` presets map to the orbit component's yaw/pitch/distance).

### 3.5 Shooter migration (`games/shooter/`)
Same pattern. Additional detail: shooter's `Transform` carries a `yaw` (ships face their heading via `headingToYaw`), so the migration maps it to `TransformComponent.rotation = glm::angleAxis(yaw, {0,1,0})`, keeping ships oriented. `Velocity`/`Health`/`Player`/`Enemy`/`Bullet` stay as game components; ships, enemies, and bullets become mesh entities; camera → `OrbitControllerComponent` from shooter's `setOrbit(0, 62, 22)`.

## 4. Data flow

```
game.onUpdate(dt):
  gameplay systems over m_scene.registry() (steering/combat/wall-bounce write TransformComponent)
  m_scene.update(dt)                     // camera controller
game.onRender:
  renderer.setLightDirection(...); renderer.setPointLights(...)
  m_scene.render(renderer, aspect)       // sets camera from primary; submits <Transform,Mesh>
  ... HUD / damage text ...
```

## 5. Testing

- **`Scene::render`** is GL-bound (constructs a `MeshRenderer` fed to the renderer) and cannot run without a GL context, so it is **screenshot-verified** — the scene layer's first piece that isn't a pure unit test. Verified via `scene_demo`/`controller_demo` (identical to pre-migration) and via arena/shooter looking the same as their baselines.
- **`MeshComponent`** is a trivial data struct (no test warranted).
- **Migrations preserve behavior:** the gameplay math is unchanged — `test_steering`, `test_wall_bounce`, `test_agent_collision`, and shooter's tests stay green (they test the free functions, which now receive `TransformComponent` fields via the game glue). Full build + suite green.
- **Regression gate (per game):** capture a pre-migration screenshot of arena and shooter, then confirm the post-migration screenshot matches (same layout, camera, colors, HUD). The controller inspects both.

## 6. Risks & mitigations

- **Arena/shooter are gameplay-heavy and screenshot-only** — the highest-risk part. Mitigation: each migration is its own task with a strict before/after screenshot gate; the gameplay unit tests pin the math; the single-`TransformComponent` rule avoids desync bugs.
- **`float scale` → `vec3 scale`** in the gameplay helpers. Mitigation: helpers keep their scalar signatures; the game passes `.scale.x` (uniform scale), a mechanical, local change.
- **Shooter ship orientation** (yaw → quat). Mitigation: `TransformComponent.rotation = angleAxis(yaw, +Y)`; verified in the shooter screenshot (ships face their heading).
- **`Scene::render` couples the scene module to the renderer.** Accepted: it's an engine-internal include (`Renderer`/`MeshRenderer`/`MatrixCamera`), forward-declared in the header; games that don't call `render` pay nothing.
- **Two-transform desync** if a game kept its old `Transform`. Mitigation: the old `Transform` structs are DELETED; there is exactly one `TransformComponent` per entity.

## 7. Open items (deferred, not blocking)

- `LightComponent` + scene-driven lighting (lights are still game-set).
- Sorting / frustum culling inside `Scene::render`; instanced submission for many identical meshes.
- Retiring the standalone `OrbitCameraController`/`FlyCameraController`/`CameraController` once all games are migrated.
- Migrating the remaining games (models, particles, camera_demo, billboard_demo) onto `Scene`.
- A `Scene::update`/`render` ordering/system-registration policy for user systems.
