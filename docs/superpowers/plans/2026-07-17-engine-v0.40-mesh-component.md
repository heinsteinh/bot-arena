# Engine v0.40 — MeshComponent + Scene::render + arena/shooter Migration Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add `MeshComponent` + `Scene::render(Renderer&, aspect)` so the scene draws its own `<Transform, Mesh>` entities; migrate the two scene demos as proof; migrate `arena` and `shooter` off their ad-hoc `entt::registry` + manual submission onto `Scene` with a single `TransformComponent`.

**Architecture:** `MeshComponent` is data. `Scene::render` sets the renderer camera from the primary camera and submits every `<TransformComponent, MeshComponent>` via an internal `MeshRenderer`. Its definition lives in a separate `SceneRender.cpp` (engine lib only) so the GL-free tests target — which compiles `Scene.cpp` directly — stays renderer-free. Games replace their own `Transform` with the engine `TransformComponent` (one source of truth), keep gameplay components in the scene registry, and call `scene.render`.

**Tech Stack:** C++17/20, EnTT, GLM, OpenGL (deferred), Catch2, CMake.

## Global Constraints

- **One transform per entity.** Games' own `Transform` structs are DELETED; entities use `engine::TransformComponent`. No two-transform sync.
- **`Scene::render` definition goes in `engine/scene/SceneRender.cpp`, added ONLY to `bot_arena_engine`** (never the `bot_arena_tests` sources). `Scene.hpp` forward-declares `class Renderer;` and only declares `render`. This keeps the tests target free of GL/renderer headers.
- **Lighting stays game-set** (`setLightDirection`/`setPointLights` before `scene.render`). No `LightComponent` this slice.
- **GLM gtc only** for any quaternion use (`glm::angleAxis` for shooter yaw); no `gtx`.

- [ ] **Step 3: `engine/scene/SceneRender.cpp`**

```cpp
#include "engine/renderer/MatrixCamera.hpp"
#include "engine/renderer/MeshRenderer.hpp"
#include "engine/renderer/Renderer.hpp"
#include "engine/scene/Components.hpp"
#include "engine/scene/MeshComponent.hpp"
#include "engine/scene/Scene.hpp"

namespace engine {

void Scene::render(Renderer& renderer, float aspect) {
  const CameraUniforms cu = cameraUniforms(aspect);
  renderer.setCamera(cu);
  MatrixCamera cam(cu.view, cu.projection);
  MeshRenderer meshes(renderer.queue(), renderer.registry(), cam);
  auto view = m_registry.view<TransformComponent, MeshComponent>();
  for (const entt::entity e : view) {
    const TransformComponent& t = view.get<TransformComponent>(e);
    const MeshComponent& m = view.get<MeshComponent>(e);
    meshes.submit(m.mesh, m.material, t.localTransform());
  }
}

}  // namespace engine
```

Apply these transformations across the file (mechanical; the screenshot gate is the correctness check):

| From | To |
| --- | --- |
| `#include "games/arena/Components.hpp"` uses of `arena::Transform` | `engine::TransformComponent` (add `#include "engine/scene/Components.hpp"`, `MeshComponent.hpp`, `ControllerComponents.hpp`) |

Specifics:
- **Walls (4) + ground:** create once as static `SceneObject`s with `TransformComponent`(translation + `scale` = the box size) + `MeshComponent{cube, wallMat|groundMat}` — moved from the `onRender` `wall(...)` lambda / ground submit into entity creation (in `spawnEntities`/`onAttach`, after materials exist — see camera/material note below). Their `TransformComponent.localTransform()` must reproduce the old `translate*scale` boxes (walls at `{0,0.5,±5}` size `{10,1,0.25}` etc.; ground at `{0,-0.05,0}` scale `{20,0.05,20}`).
- **Player + bots:** `MeshComponent{cube, playerMat}` / `{cube, botMats[i%4]}` assigned at creation (bot color fixed per-bot).
- **Materials + cube handle** need the `Renderer` (registered in `ensureResources`). Entities are created in `onAttach`/`spawnEntities` before the renderer exists. Resolve by: create the entities + gameplay components in `onAttach`, but assign `MeshComponent` (which needs `cube`+material handles) lazily in `ensureResources` (first `onRender`) by iterating the entities and adding a `MeshComponent` based on their tag (Player/Bot/wall/ground). OR register materials + build the mesh entities entirely in `ensureResources` on the first frame while keeping the deterministic warm-up in `onUpdate`. Choose whichever keeps the warm-up deterministic; document the choice in the report.
- **`onRender`:** delete the `MeshRenderer`/`wall` lambda/`view<Transform>` submission; set lights (as today) then `m_scene.render(renderer, aspect)`. Keep the HUD (`HP`/`Kills`) and any damage text.
- **Camera:** replace `m_camera.setTarget(...)`/`setOrbit(45,55,18)`/`update(dt)`/`camera()` with a camera `SceneObject`: `m_camera = m_scene.createObject("Camera"); m_camera.addComponent<engine::CameraComponent>(); auto& oc = m_camera.addComponent<engine::OrbitControllerComponent>(); oc.targetPoint = {0,0.5,0}; oc.yaw = 45; oc.pitch = 55*? ...`. NOTE the v0.39 orbit convention: pitch is ELEVATION (positive = above). The old `setOrbit(yaw=45, pitch=55, distance=18)` used the old controller's spherical convention (pitch = elevation above target) — map `oc.pitch = 55` (already elevation) and clamp within `maxDistance` (raise `oc.maxDistance` to ≥18 and set `oc.distance = 18`). Drive it with `m_scene.update(dt)` in `onUpdate`. `BOTARENA_ORBIT` presets (if arena reads them) map onto `oc.yaw`/`oc.pitch`.
